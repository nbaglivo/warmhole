warmhole

A warm little portal from your static site into the fediverse. A small Hono and Fedify server that turns a static site's feed into a fediverse account people can follow. You run your own copy, and one copy can serve a few sites.

design

1. Components

Everything runs in one container. The left column handles pings from your site, the right column handles messages from other servers, and both meet in SQLite.

request response signed ActivityPub traffic
UnitDoesDepends on
configLoads and validates the sites file and reads tokens from env.nothing
feedFetches a feed and turns RSS, Atom or JSON Feed into the same entry shape: id, url, title, summary, html, published, updated.fetch, a feed parser
diffCompares entries with stored posts and returns what to create, update and delete. Has no I/O.nothing
storeKeys, followers and posts tables behind a small interface.node:sqlite
federationFedify setup: actor, outbox, followers and post routes, inbox listeners, key pairs and sending.Fedify, store
syncRuns one sync for a site: feed, then diff, then store, then send.feed, diff, store, federation
appThe Hono app: sync and health routes, with Fedify mounted as middleware.everything above

2. Stored data

Three tables of our own, plus Fedify's storage and queue tables in the same file.

TableColumnsWhy
keyssite_id, kind (RSA or Ed25519), private and public keyCreated on first start. Config never holds keys.
followerssite_id, actor_id, inbox, shared_inbox, created_atWho to deliver to. Deleted on Undo(Follow).
postssite_id, entry_id, slug, title, summary, html, url, published, updated, content_hash, deleted_at, pending_activityRemembers what was sent, and serves each Article at its own URL even if the feed changes.

3. Syncing a site

The ping only answers once the feed has been read and the changes are saved. Delivery happens after the response, so a slow follower server never makes CI wait.

Entry in feed vs. posts tableResult
Not stored yetSave it and send Create(Article)
Stored, content hash changedUpdate it and send Update(Article)
Stored, hash unchangedNothing
Stored, gone from the feedMark deleted and send Delete, only if the site sets deleteMissing. Off by default, because many feeds only list recent posts.
First sync of a new siteSave everything and send nothing, so existing posts don't flood followers' timelines.

Guards that stop a sync before it changes anything: the feed can't be fetched or parsed (502), the feed has no entries (422), or the feed would delete more than half the stored posts (422). The last one catches a broken build that publishes an almost empty feed.

4. Following

Fedify checks every incoming signature before our code runs. Our listener only stores or removes a follower and asks Fedify to send the reply.

5. Discovery across two domains

WebFinger on the server is a small route of our own, not Fedify's. Your site answers one question: which actor does the handle belong to? The server answers the same question the other way round, so Mastodon trusts the handle wherever it first sees the account.

6. Configuration and site setup

One JSON file for the server, with secrets kept in env. Each site needs two small additions.

{
  "publicUrl": "https://ap.nbaglivo.dev",
  "sites": [
    {
      "id": "inner-monologue",
      "handle": "nico",
      "domain": "innermonologue.nbaglivo.dev",
      "feedUrl": "https://innermonologue.nbaglivo.dev/feed.xml",
      "name": "The Open Inner Monologue",
      "summary": "The open inner monologue of Nicolás Baglivo.",
      "icon": "https://innermonologue.nbaglivo.dev/public/icons/avatar.png",
      "syncTokenEnv": "INNER_MONOLOGUE_SYNC_TOKEN",
      "deleteMissing": true
    }
  ]
}

On the site: a static /.well-known/webfinger file, served as application/jrd+json. The server prints this file for each site on request (GET /sites/:id/webfinger.json), so nobody writes it by hand.

{
  "subject": "acct:nico@innermonologue.nbaglivo.dev",
  "links": [
    {
      "rel": "self",
      "type": "application/activity+json",
      "href": "https://ap.nbaglivo.dev/users/inner-monologue"
    }
  ]
}

In CI: one step after deploy.

- name: Notify fediverse server
  run: >
    curl --fail --retry 3 -X POST
    -H "Authorization: Bearer ${{ secrets.FEDI_SYNC_TOKEN }}"
    https://ap.nbaglivo.dev/sites/inner-monologue/sync

7. Errors and safety

  • Sync tokens are compared in constant time. A wrong token gets 401, and so does an unknown site id, so ids can't be probed.
  • Feed fetches time out after 10 seconds and stop reading after 5 MB.
  • Inbox requests with bad signatures are rejected by Fedify. Activities we don't handle get 202 and are dropped.
  • Deliveries retry with backoff through Fedify's queue. When Fedify reports that an inbox is gone for good (404, 410, or too many failures), followers using it are removed.
  • Logs use LogTape, which Fedify already uses, as JSON lines on stdout.

8. Testing

  • Unit: feed normalizing against real RSS, Atom and JSON Feed samples, including your feed.xml; every row of the diff table and every guard; config validation.
  • Integration: the Hono app with SQLite in memory. Ping it with a local feed, then check the stored posts, the queued activities and the HTTP responses. A fake follower server checks that signed deliveries arrive.
  • By hand before release: fedify lookup on the actor, fedify inbox as a throwaway follower, then a real follow from a test Mastodon account.

9. Repository and stack

  • The written spec lives next to this page, in docs/superpowers/specs/2026-10-15-warmhole-design.md.
  • TypeScript, run directly by Node 26 with no build step. Tests with node:test. Node version pinned in mise.toml.
  • Dependencies: hono, @hono/node-server, @fedify/fedify, @fedify/hono, @fedify/sqlite and a feed parser.
  • A Dockerfile based on node:26-slim, with SQLite on a mounted volume.

10. What changed after checking Fedify

  • WebFinger is our own handler. Fedify's built-in WebFinger uses one handle domain for the whole server, so it can't answer with a different domain per site. A small Hono route answers instead, before Fedify.
  • Handles are unique per server. When Mastodon meets the actor first, it asks the server about nico@ap.nbaglivo.dev, and that has to name exactly one site. The config check rejects duplicate handles.
  • Sends are marked pending first. Fedify's queue can't join our database transaction, so each changed post is saved with a pending activity, handed to the queue, then cleared. A crash in between is finished by the next ping.
